01 / The boundary

Your machine is just a client

Telegram sessions, Bot credentials and the encrypted cache stay on the server. The CLI needs only the API URL and API bearer token.

Why keep Telethon?

The service reads a personal account. Contacts, dialogs, old messages, search and complete albums still need that account’s session.

What does the Bot add?

Supported metadata and exact private messages observed through a verified Business/Secretary connection. Its cache is a partial live view, never a full history.

02 / Choosing a provider

Capability first. Safe fallback second.

off

Telethon only. No Bot polling. Default configuration and rollback switch.

shadow

Validate and collect Bot updates. All public reads still use Telethon.

primary

Prefer Bot-supported reads when identity and cache freshness checks pass.

Fallback has limits. A cache miss or eligible timeout can fall back once. Bot 401, 429 and owner mismatch cannot be hidden by switching providers. Telethon-only operations remain independent.

03 / Keeping cached data trustworthy

Store first. Acknowledge afterward.

The poller receives Business/Secretary updates, verifies which owner and connection they belong to, then commits the entire batch and its next cursor together. Only the next poll acknowledges that committed cursor.

Identity + privacy

  • Ordinary conversations with the bot never become personal-account messages.
  • AES-GCM encrypts records; HMAC hides lookup identifiers.
  • The root key is separate from SQLite. Default retention is 30 days.

Freshness + revocation

  • Failed polling disables cached reads until catch-up.
  • Connection edits/disable clear messages; 24-hour polling gaps clear stale data.
  • A week without updates resets ordering safely for Telegram’s possible ID reset.
What happens during a download?

The gateway selects a cached message, preflights its file, then rechecks the live record and provider state after each await. Deletion, edits, revocation or a concurrent 401/429 can invalidate it before response headers. Invalidated streams are closed.

After streaming begins, an upstream failure aborts the transfer and updates health. It cannot start a second provider response. Cleanup also runs if the client leaves before the first byte.

04 / Agent workflow

Install → log in → discover → read

On the client machine

python3 install-tg.py
tg login --url https://your-api.example
tg auth-status --remote
tg operations list
tg chats list
tg messages search --query "meeting"
tg messages get --chat-id 123456 --message-id 42

Download install-tg.py from a published GitHub release. Requires Python 3.12+ on macOS/Linux. The URL above is a placeholder.

What gets installed?

  • Isolated CLI environment and ~/.local/bin/tg.
  • Managed skill at ~/.agents/skills/tg and a Claude compatibility link.
  • Bash, Zsh and Fish completions, generated from the command parser.

Open a new shell and ensure ~/.local/bin is on PATH. Unrelated files are preserved; setup conflicts produce warnings.

Credentials, downloads and direct pip installs

tg login prompts privately for the API token and saves URL-bound credentials with mode 0600. Automation can use TG_API_URL and TG_API_TOKEN, or --token-stdin. Never paste secrets into agent chat. Redirects and automatic retries are disabled.

tg media list --chat-id 123456 --message-id 42
tg media download --chat-id 123456 --message-id 42 \
  --media-id 42:0 --output ./download.bin

Use IDs returned by the API. Downloads require an explicit file and preserve existing files unless --overwrite is supplied. JSON goes to stdout, errors to stderr.

Python wheels have no standard postinstall hook. Direct pip/wheel installations require tg skill install and tg completion install. The release installer runs both automatically. For managed dotfiles use tg completion install --no-shell-init and integrate through the configuration manager.

05 / Keeping the pieces aligned

One contract. One release version.

API → CLI contract

FastAPI generates OpenAPI. A checked snapshot ships inside the CLI. Commands use its parameter types; a reviewed mapping supplies friendly names.

CI rejects a stale snapshot, uncovered endpoint, duplicate operation ID or unsupported contract shape. Completion uses the same parser. Update the bundled skill alongside user-facing changes.

Main → GitHub release

Successful main-push CI triggers paired API/CLI builds. Automatic versions increment x.(y+1).0; the workflow UI also accepts a higher explicit X.Y.Z.

Both wheels and source packages ship with checksums and the installer. Builds stamp versions without committing a bump. Retry-safe publication can resume interrupted drafts.

Release is not deployment. Publishing makes installable artifacts available. Starting/upgrading the API and enabling Bot collection remain separate operator actions.

Change

Typed routes + DTOs + tests; update CLI mappings and agent examples when needed.

Regenerate and check

.venv/bin/python scripts/export_openapi.py
make check

Ruff, strict typing, schema parity and both test suites. Each package has an 80% coverage floor. Locked dependencies align local, Docker, CI and release environments.

Review, merge, release

PR checks validate Python 3.12/3.14, all completion shells and Docker. After an authorized merge, successful main CI triggers publication. Installer smoke testing uses the actual built wheel.

Operational boundaries: one process, one poller, one session owner. Keep Bot mode off until the owner approves the disclosed use under Telegram’s current terms. Real-account tests require explicit configuration and exclusive session ownership. Code/tests do not establish live acceptance.

Operator activation checklist
  1. Protect a non-local API with bearer authentication.
  2. Configure server Bot token, matching owner ID and a separate random 32-byte cache key.
  3. Start shadow mode, enable Secretary Mode and connect the owner’s selected chats. A fresh reconnect may be needed to discover the connection.
  4. Inspect the health body: both providers healthy, poller running, connection verified. HTTP 200 alone is not readiness proof.
  5. Deliberately switch to primary after validation. Switch to off to roll back. Never run two pollers or reuse the session concurrently.

Existing webhooks require an operator decision; startup never deletes them. Cache key rotation must preserve the separate Telethon session.
